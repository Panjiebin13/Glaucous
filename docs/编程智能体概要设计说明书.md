# Glaucous 编程智能体概要设计说明书

- 版本：v4.1（2026-08-27）
- 命名：**Glaucous**（海鸥灰蓝 · 雨过天青），命令 `glaucous`
- 一句话定位：*“雨过天青，海鸥滑翔，代码自有清凉。”*
- 定位：一个清爽、可控的 CLI 编程智能体——默认以 **Plan 模式**（只读）探索需求并产出方案，经用户授权后切换 **Build 模式**执行修改；在**工作区沙箱 + 分级审批**约束下自主读写文件、执行命令；具备 glaucous.md 规则记忆、事实记忆、skill 注册、多模型注册切换等扩展机制。对标 Claude Code / Codex CLI，界面学其安静与密度，视觉自成清凉体系。

---

## 1. 项目概述

### 1.1 题目硬约束与设计响应对照

| 题目要求 | 本设计对应 |
|---|---|
| 禁用 agent 框架 / SDK | 全部核心逻辑自研，仅用 OpenAI 兼容客户端作 HTTP 通道（§3） |
| 禁用服务端托管工具 | 工具全部本地执行（文件系统 / shell 子进程），无 Code Interpreter / Files API（§5） |
| 自研：对话历史与上下文管理 | 分级截断 + 上下文压缩 + 占用比可视化（§4.2） |
| 自研：工具定义与本地执行 | 工具注册表 + 双层权限（声明层隐藏 + 执行层审批）+ 工作区沙箱（§5） |
| 自研：模型输出解析 | 流式 tool-call 拼装 + schema 校验 + 容错回喂（§4.3） |
| 自研：循环终止条件 | 五类终止条件 + 守卫检查点（§4.1） |
| 自研：错误处理 | 分层错误处理表 + 熔断（§4.4） |
| 凭据不入库 | 环境变量引用 + gitignore 配置文件（§9） |

### 1.2 设计目标

1. **可用**：端到端完成真实任务（修 bug、加功能、写测试），不只会聊天。
2. **可控**：Plan/Build 两模式 + 工作区沙箱 + 分级审批，任何操作路径可审计。
3. **可解释**：先方案后动手，每步动作可见，会话落盘可复盘。
4. **可成长**：glaucous.md 规则记忆 + 事实记忆沉淀经验，skill 注册扩展领域能力。
5. **清凉**：Glaucous 主题——天青底色、海鸥意象、克制的视觉音量（§8）。
6. **可评测**：自建任务集回归，有成功率数据支撑（答辩素材）。

### 1.3 非目标（明确不做）

多模态、Web/GUI 界面、多 agent 协作、模型训练/微调、IDE 插件集成。

## 2. 总体架构

### 2.1 分层架构图

```
┌────────────────────────────────────────────────────────────────┐
│  CLI 交互层    REPL / 流式渲染 / Glaucous 主题 / 审批卡片 / 占用条 │
├────────────────────────────────────────────────────────────────┤
│  Agent 编排层  loop / state / guard（终止守卫）/ plan↔build 切换  │
├──────────┬──────────┬───────────┬───────────┬──────────────────┤
│ 上下文管理 │  工具系统 │  权限体系   │  扩展子系统 │  LLM 网关        │
│ history  │ registry │ workspace │ glaucous │  models 注册表    │
│ budget   │ executor │ plan/build│  .md 规则 │  client/stream   │
│ compactor│ declarator│ approval │ memory   │  retry 退避      │
│          │          │           │ skills   │                  │
├──────────┴──────────┴───────────┴───────────┴──────────────────┤
│  本地执行环境    文件系统 / shell 子进程(asyncio)                  │
└────────────────────────────────────────────────────────────────┘
```

各层只依赖下层接口：`loop` 不感知具体工具实现与 UI；`tools` 不感知 LLM 细节；扩展子系统以独立模块挂接，互不耦合。

### 2.2 核心工作流（Plan → Build 循环）

```
启动（默认 Plan 模式）
  → 用户输入需求
  → Plan 模式：只读探索（读文件/搜索/只读命令）→ 产出方案
  → 请求切换 Build，用户三选一：
      ① 开始构建·每次请求权限 → Build(per-action)
      ② 开始构建·同意所有权限 → Build(auto-approve)
      ③ 继续讨论一下          → 留在 Plan，修订方案
  → Build 模式：按授权策略执行修改（写操作审批或放行）
  → 任务完成 → 回到 Plan 模式，等待下一个需求
```

### 2.3 一次工具调用的数据流

```
LLM 返回 tool_calls
  → 声明层检查（Plan 模式下写工具根本未注册，无从调用）
  → 执行层：工作区沙箱校验 → 危险级别分类 → 授权策略匹配
      ├─ 放行 → 执行 → 输出截断 → 结果回填 → 回到 LLM
      └─ 拦截 → 审批卡片（同意 / 同意同类型 / 拒绝）→ 决策回喂
```

## 3. 技术选型与理由

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 开发效率高；asyncio 子进程编排直观；核心逻辑薄、易单测 |
| 运行平台 | Linux 一等公民（WSL2 开发），跨平台兼容 | 命令分类器/进程管理只有一套 POSIX 语义；pathlib + UTF-8 显式声明 + CRLF 归一化三点保证可移植 |
| LLM 接入 | OpenAI 兼容客户端 + 原生 tool calling | 只把 SDK 当 HTTP 客户端；不使用任何服务端托管工具 |
| 终端 UI | rich（Theme/渲染/diff）+ prompt_toolkit（输入） | 少造轮子；rich 的 Theme 机制原生支持 Glaucous 色板 |
| 配置 | TOML（tomllib 标准库） | 无额外依赖，人类可读可编辑 |
| 测试 | pytest + mock LLM | 循环逻辑可脚本化回放验证 |
| 分发 | pyproject.toml，`pipx install` | 安装体验好，演示方便 |

## 4. 核心引擎设计（自研重点）

### 4.1 Agent 主循环与终止条件

**状态机**：`RUNNING → WAITING_TOOL → WAITING_APPROVAL → RUNNING → … → DONE / ABORTED`，外加 `WAITING_USER`（ask_user / 审批 / Plan→Build 确认时挂起）。

**主循环骨架**（面试讲解核心）：

```python
async def run(self, task: str) -> str:
    self.history.push_user(task)
    while True:
        self.guard.check(self.steps, self.budget)    # 任何请求前先过守卫
        tools = self.tools.expose(self.mode)          # 声明层权限：模式决定可见工具
        msg = await self.llm.stream(self.history.view(), tools)
        self.steps += 1
        if not msg.tool_calls:
            return msg.text                           # ① 自然终止
        for call in msg.tool_calls:
            result = await self.tools.dispatch(call)  # 执行层权限：沙箱+分类+审批
            self.history.push_tool(result)            # 含输出截断
```

**五类终止条件**（题目点名要求）：

| # | 条件 | 触发点 | 说明 |
|---|---|---|---|
| 1 | 自然终止 | 模型无 tool_calls | 正常完成 |
| 2 | 步数上限 | 默认 50 步，可配 | 防死循环的硬熔断 |
| 3 | Token 预算耗尽 | 压缩后仍超限 | 优雅终止并汇报已完成部分 |
| 4 | 用户中断 | Ctrl+C / `/stop` | kill 当前子进程，保留现场可继续 |
| 5 | 重复失败熔断 | 连续 3 次同参数调用失败 | 停止 + 生成诊断报告 |

守卫检查点固定放在"每次请求 LLM 之前"，保证无论循环从哪条路径回来都会重新评估终止条件。

### 4.2 对话历史与上下文管理

**消息模型**（OpenAI 角色语义，自管理）：

```python
Message = System(prompt + glaucous.md 规则 + 事实记忆 + skill 索引)
        | User(text)
        | Assistant(text?, tool_calls?)
        | Tool(call_id, content, ok)
```

- **持久化**：会话追加写 `.glaucous/sessions/<id>.jsonl`，支持 `--resume` 续聊。
- **Token 记账**：消息粒度估算（字符数/4，中文按/1.5），支持接 tokenizer 精确计数；维护累计值。

**分级截断策略**（三级递进）：

| 级别 | 触发 | 动作 |
|---|---|---|
| L0 工具输出截断 | 单个结果 > 300 行 / 50KB | 完整输出落盘 `.glaucous/outputs/<call_id>.log`；历史中替换为"头 200 + 尾 50 + 省略标记 + 回取提示" |
| L1 历史裁剪 | 预算占用 > 70% | 从旧到新淘汰已完成轮次的 tool 结果正文，替换为**本地派生的调用摘要**（见下）；保留 assistant 文本 |
| L2 上下文压缩 | 预算占用 > 85% | 用模型把早期历史压成任务摘要，替换为一条 summary 消息；保留 system + 最近 K 轮原文 + 方案轻量锚与任务清单 |

**L0 不丢信息——完整输出可回取**：截断只影响"注入上下文的正文"，不丢弃数据。完整输出在截断时落盘；截断消息尾部附带一行提示（"完整输出已保存，可调用 read_output 查看"）。模型在需要时用 `read_output(call_id, offset, limit)` 分段读取任意区间——大输出通常只有头尾有用，模型自主决定是否回取。

**L1 调用摘要的来源——执行时记账，裁剪时派生**：摘要不调用模型生成，而是在**工具执行时**顺手记录结构化元数据，L1 触发时本地拼接为一行：

```python
# dispatch 时记录（零额外成本）
ToolResult.metadata = {
    "tool": "edit_file", "args_brief": "src/auth/session.py",
    "ok": True, "duration_ms": 120, "lines": 24,
}
# L1 裁剪时派生摘要（确定性拼接，无幻觉风险）
"⎿ edit_file src/auth/session.py · 成功 · 120ms · 24 行"
```

理由：摘要的作用是让模型记得"做过什么"而非"内容是什么"；元数据本地派生零 token 成本、结果确定、即时可用，而模型生成摘要既花钱又有幻觉风险。若模型确需历史细节，可经 `read_output` 回取（L0 已落盘）。

**上下文占用可视化**：每轮交互结束在状态栏渲染占用条，随阈值变色（低→海草绿 / >70%→落日橙 / >85%→陶土红），超阈值时提示朴素直白：「🌊 上下文压缩中」。

占用数据由 budget 记账器驱动，与截断策略共用同一套阈值常量，保证"用户看到的"与"系统执行的"一致。

**设计辩护**：L0 保真（正文截断但数据可回取）、L1 低成本（摘要本地派生零 token）、L2 保意图（截断丢任务目标导致行为漂移）；压缩时显式保留"方案轻量锚 + 任务清单"——Build 模式的执行锚点，压缩后不跑偏的关键。

### 4.3 模型输出解析

- **首选原生 tool calling**：流式增量按 `tool_call delta` 的 index 顺序拼装 `arguments`，完成后 `json.loads` + schema 校验。
- **容错策略**（全部自研）：

| 异常 | 处理 |
|---|---|
| arguments JSON 非法/不完整 | 生成错误 tool 消息回喂，模型自行修正（最多 2 轮） |
| schema 校验失败 | 同上，错误信息指明具体字段 |
| 幻觉调用未注册工具 | 返回"工具不存在 + 可用工具列表"（Plan 模式下写工具被幻觉调用时，回喂"当前为 Plan 模式，请先产出方案"） |
| 流中断 | 断点重发当前请求（messages 未变，幂等） |

- **P1 兜底**：纯文本协议解析（`<tool_call>{json}</tool_call>`），兼容不支持 function calling 的网关。

### 4.4 错误处理与鲁棒性

| 层 | 错误 | 处理 |
|---|---|---|
| 工具执行 | 异常/非零退出 | `ok=False` + stderr 回喂，模型自纠 |
| LLM API | 429 / 5xx / 超时 | 指数退避 + 抖动重试（最多 4 次），UI 提示 |
| 上下文 | 超限 | 触发 L1→L2；压缩后仍超 → 优雅终止汇报 |
| 逻辑 | 死循环倾向 | 重复调用熔断（§4.1-⑤） |
| 系统 | Ctrl+C | kill 子进程 + 保留现场，可继续对话 |

## 5. 会话模式与权限体系（产品第一亮点）

安全体系由四个正交概念组成：**会话模式**（Plan/Build）、**授权策略**（Build 内的审批粒度）、**操作危险级别**（动作属性）、**工作区边界**（空间范围）。权限执行分**声明层**与**执行层**双层。

### 5.1 Plan / Build 双模式

| | Plan 模式（默认） | Build 模式 |
|---|---|---|
| 语义 | 探索与规划：只读 | 实施与修改：可写 |
| 可用工具 | 读/搜索/只读命令/ask_user/memory/todo/submit_plan | 全部工具 |
| 写工具 | **声明层隐藏**（tools 参数中不存在） | 按授权策略执行 |
| 产出 | 方案（Plan Document） | 代码修改、命令执行结果 |
| 进入方式 | 启动默认 / 任务完成后自动回归 / `/plan` | 方案确认后切换 / `/build` |

**双层权限设计**（核心亮点）：

1. **声明层（declarator）**：Plan 模式下，写类工具根本不出现在发给 API 的 `tools` 定义里——模型从源头无法调用，而非调用后拦截。省一轮失败交互，也杜绝"模型试探越权"。
2. **执行层（approval）**：Build 模式下，写操作按授权策略走审批；所有模式共享工作区沙箱与危险命令分类。

bash 工具的特殊处理：两种模式都注册 `bash`，但 Plan 模式下命令分类器只放行 SAFE 白名单（ls/cat/grep/git status/运行测试等只读命令），写类命令被拦截并回喂"当前处于 Plan 模式，该命令会修改状态"。

### 5.2 Plan → Build 切换协议

Plan 模式产出方案后，agent 请求切换，用户面对**一次性三选一**（界面样式见 §8.4）：

- **授权策略语义**：①进入 `Build(per-action)`；②进入 `Build(auto-approve)`；③留在 Plan，agent 根据反馈修订方案，可再次请求切换。
- **策略作用域**：授权仅对**当前构建过程**有效——任务完成回归 Plan 后，下一个需求重新走方案→授权流程；策略不跨会话持久化。
- **auto-approve 的安全例外**（设计底线）：即便选择"同意所有权限"，以下两类操作仍单独醒目确认——
  a. **工作区外**的任何读写（信任边界不可被批量授权跨越）；
  b. **破坏性命令**（`rm -rf`、`git push --force`、`sudo`、`curl | sh` 等模式表命中项）。
  理由：用户授权的是"构建本项目"，不可逆的区外/破坏性操作超出该授权语义；业界同类产品的全放行模式同样保留此类拦截。
- 方案文档落盘 `.glaucous/plans/<id>.md`。**上下文注入采用轻量锚策略**：Build 执行期间不把完整方案写入上下文，而是注入一条轻量锚——`方案已就绪：.glaucous/plans/<id>.md（目标一行 + 未完成任务清单）`，并注册 `read_plan` 工具供模型按需回读全文。方案全文通常数百行，常驻注入会挤占预算；轻量锚保证模型始终"知道方案在哪、当前该做什么"，细节需要时再回读——与 L0 截断的存档回取思想一致。

### 5.3 Build 模式审批（per-action 策略）

```
写操作被拦截
  → 审批卡片（海盐青描边；破坏性命令陶土红警示 + 命令全文/diff）
  → 三选项：
      [a] 同意           —— 仅放行本次
      [b] 同意同类型      —— 本会话内同类操作（按工具粒度：edit_file / bash 等）不再询问
      [c] 拒绝（可附理由）—— 生成 Tool 消息"用户已拒绝：{理由}"，模型改道
```

- 拒绝结构化回喂理由，模型理解"为什么被拒"并调整策略，而非原样重试触发熔断。
- 审计：每次审批决策（时间/工具/参数/用户选择）追加写 `.glaucous/audit.log`。

### 5.4 工作区（Workspace）

- **定义**：启动时 `glaucous --workspace <dir>` 打开指定文件夹为工作区；**未指定时默认以当前目录为工作区**。路径经 `realpath` 规范化。
- **边界规则**：区内操作按模式/策略执行；**区外读写任何模式下都走单独审批**（含 auto-approve，见 §5.2）。
- **逃逸防御**：`realpath` + 符号链接解析后前缀校验，防 `../` 穿越与符号链接逃逸；shell 命令中的路径参数同样规范化检查。
- **只读白名单**：配置中可显式追加区外只读路径（JDK 目录、`~/.m2` 等），环境探测免审批。

### 5.5 危险级别分类

| 级别 | 判定 | 例子 | 处理 |
|---|---|---|---|
| SAFE | 白名单语义 | `ls`、`cat`、`grep`、`git status`、运行测试 | Plan/Build 均放行 |
| WRITE | 修改区内状态 | `write_file`、`edit_file`、`git commit` | Build 审批（按策略） |
| DANGEROUS | 模式表命中 | `rm -rf`、`sudo`、`git push --force`、`curl \| sh`、写区外 | **永远单独醒目确认** |

bash 分类器 = 首命令词白/黑名单 + 参数模式匹配；**无法判定时保守升级**为 WRITE 走审批——宁多问不漏放。

### 5.6 工具清单

| 工具 | 参数要点 | 设计要点 | 模式 |
|---|---|---|---|
| `read_file` | path, offset?, limit? | 带行号；区外触发审批 | 两模式 |
| `list_dir` / `glob` / `grep` | path / pattern / regex | 浏览与搜索 | 两模式 |
| `bash` | command, timeout?, background? | cwd=工作区；分类器定级；Plan 仅 SAFE | 两模式 |
| `read_output` | call_id, offset?, limit? | 回取 L0 落盘的完整工具输出（分段读取，见 §4.2） | 两模式 |
| `read_plan` | plan_id? | 回读方案文档全文（轻量锚的回取通道，见 §5.2） | 两模式 |
| `ask_user` | question, options? | 环境求助/需求澄清（§7.1） | 两模式 |
| `memory_save` | content, scope, category | 事实记忆写入（§7.2） | 两模式 |
| `todo_write` | todos[] | 计划清单；Plan 产出任务、Build 勾选进度 | 两模式 |
| `submit_plan` | plan(结构化方案) | Plan 模式产出方案并触发切换确认（§5.2） | 仅 Plan |
| `write_file` | path, content | 审批卡片附 diff | 仅 Build |
| `edit_file` | path, old, new, replace_all? | 精确唯一匹配，否则报错回喂 | 仅 Build |
| `load_skill` | name | skill 惰性加载（§7.3） | 两模式 |

`edit_file` 唯一匹配约束：强迫先 read 后 edit；歧义回喂模型而非静默选择。

## 6. LLM 网关与模型注册

### 6.1 模型注册表

`models.toml`（入 gitignore，key 走环境变量引用）注册多个模型档案：

```toml
[models.deepseek]
base_url = "https://api.deepseek.com/v1"
api_key_env = "DEEPSEEK_API_KEY"     # 只存变量名，不存值
model = "deepseek-chat"
temperature = 0.2

[models.local-qwen]
base_url = "http://localhost:11434/v1"
api_key_env = "LOCAL_LLM_KEY"
model = "qwen3-coder"
```

- **注册入口**：手工编辑，或 `/model add` 向导命令（name/base_url/model/环境变量名）。
- **校验**：注册时发最小 ping 请求验证连通性，失败即时报错。

### 6.2 运行时切换

- `/model`：列表展示（当前档案高亮，含连通状态）；`/model <name>` 即时切换。
- **切换语义**：上下文为 OpenAI 通用消息结构，切换只改后续请求路由，历史无缝保留——不同模型接力同一任务是天然演示亮点。
- 档案注册时验证 tool calling 能力，不支持时自动降级文本协议（P1 兜底）。

## 7. 记忆与扩展子系统（产品第二亮点）

### 7.1 ask_user：环境难题求助通道

- **典型场景**：找不到 JDK / 特定版本解释器 / 内网凭证 / 任务歧义。
- **契约**：`ask_user(question, options?)`——问题具体可答，options 提供候选（`["/usr/lib/jvm/java-8", "帮我自动搜索", "跳过构建"]`）。
- **system prompt 引导**：环境类失败重试 2 次无果应求助而非死磕。
- **联动**：回答含环境事实（解释器路径）→ 提示调用 `memory_save` 沉淀，下次直接命中。

### 7.2 双层记忆：glaucous.md 规则 + 事实记忆

记忆按性质分两层，职责严格分离：

| 层 | 文件 | 内容性质 | 示例 | 写入方 |
|---|---|---|---|---|
| **规则层 glaucous.md** | 全局 `~/.glaucous/glaucous.md` + 项目 `<workspace>/glaucous.md` | 规范性（应当如何做） | "Java 项目统一 Java 8"、"提交信息用中文"、"本库禁止改动 generated/ 目录" | 用户手写 / `/init` 生成 / 会话中说"记住这条规则"经确认追加 |
| **事实层 memory** | 全局 + 项目（`memory_save` 作用域参数） | 经验性（环境是什么样） | "本项目解释器在 ~/.venvs/p311/bin/python"、"构建用 make dev" | agent 调用 `memory_save`；会话结束自动提炼候选（须用户确认） |

- **注入规则**：两层均注入 system prompt 尾部独立段落；**glaucous.md 全量注入永不裁剪**（规则被裁剪等于没规则，超长时提示用户精简）；事实记忆条目数超限时按 category 与最近使用加权裁剪。
- **分工辩护**：规则跨任务稳定、必须全量生效；事实随环境变化、可增删可淘汰。混存会导致"过时事实"与"有效规则"互相污染。
- **管理**：`/memory` 查看/新增/删除事实；`/rules` 查看 glaucous.md；`/init` 扫描项目生成初始规则草稿。

### 7.3 Skill 注册系统

- **Skill 定义**：目录 + `SKILL.md`，frontmatter 声明元信息，正文为指令流程：

```markdown
---
name: deploy-test
description: 将当前项目部署到测试环境并冒烟验证
---
# 部署流程
1. 运行 make build ...
```

- **注册路径**：`~/.glaucous/skills/`（全局）与 `<workspace>/.glaucous/skills/`（项目），目录即注册，启动扫描。
- **惰性加载两段式**：启动时仅注入 `name + description` 索引（<30 token/个）；模型判断相关时 `load_skill(name)` 取正文，仅本会话生效。
- **管理**：`/skills` 列表与加载状态。内置 2 个示例 skill（`code-review`、`release-checklist`）。

### 7.4 Plan 模式的方案产出

规格驱动流程融入 Plan 模式的产出结构——方案文档模板由 system prompt 引导：

```
方案（Plan Document）
├── 目标：需求复述与边界
├── 澄清：歧义点与已确认的决策（复杂任务经 ask_user 访谈）
├── 设计：技术要点、涉及文件、接口草案
├── 步骤：任务清单（联动 todo_write，Build 阶段逐项勾选）
└── 风险：可能的坑与回退方式
```

- 简单任务产出轻量方案（目标+步骤），复杂任务自然展开为完整结构——**一种模式覆盖两类任务**，概念负担最小化。
- 方案落盘 `.glaucous/plans/<id>.md`；Build 执行期间注入上下文，压缩时显式保留（§4.2）。

## 8. CLI 交互与视觉设计（Glaucous 主题）

### 8.1 设计哲学：学 Claude Code 的安静，自成 Glaucous 的清凉

界面语言取两家之长：

- **学 Claude Code**：信息密度与低视觉噪音——无框优先、固定符号语言、渐进披露、安静的成功。大量操作发生时界面依然可扫读，**视觉音量只在需要人介入时才升高**。
- **Glaucous 自有**：色彩系统与意象命名。每个颜色都从「雨过天青的晴空 + 海鸥掠过 + 夏日海风」的画面取色；意象（🕊 海鸥、☁ 云、🌊 潮汐、🌅 落日）贯穿交互文案，形成可讲述的产品气质：**可控的自由**。

### 8.2 色彩系统

**品牌色板**：

| 角色 | 色值 | 出处（意象） | 用途 |
|---|---|---|---|
| 天青主色 | `#3AA6B9` | 汝窑天青釉，晴雨初霁的天空 | 品牌标识、Plan 徽标、进度条主体、强调 |
| 海鸥白 | `#EAF4F4` | 海鸥腹羽、浪尖泡沫 | 正文、高对比文字 |
| 深海蓝 | `#1B2A4A` | 深海/暮色 | 背景基底（深邃不压抑） |
| 海盐青 | `#9BD1D9` | 近岸浅海 | 次级文字、卡片描边、思考流 |
| 晚霞橙 | `#F4A261` | 海边落日 | 警告、需注意项（少量点缀） |
| 晴空灰 | `#5A7A8C` | 晴空薄云 | 占位、禁用、弱化、快捷键提示 |

**语义色**（均在蓝色系内调和，避免破坏清凉感）：

| 语义 | 色值 | 说明 |
|---|---|---|
| 成功 | `#7FB685` 海草绿 | 清爽的绿，不带警示感 |
| 错误 | `#E07A5F` 陶土红 | 暖色里最克制的红 |
| 审批/确认 | `#F4A261` 落日橙 | 需要人介入时用 |
| 链接/工具名 | `#6BB7C9` 亮青 | 强调可交互元素；Build 徽标 |

配色比例约束：天青系 + 中性 ≥ 95%，语义色只在必要处出现——**清凉感来自克制，不来自堆色**。

### 8.3 布局原则（取自 Claude Code 的四条）

| 原则 | 含义 | Glaucous 实现 |
|---|---|---|
| **无框优先** | 常规操作不画面板，只有关键时刻（审批/提问/方案确认/危险警示）才升格为卡片 | 工具调用渲染为单行 + 缩进结果，四个关键卡片用完整 Panel |
| **固定符号语言** | 少量语义符号全程一致，降低认知负担 | `⏺` 动作行、`⎿` 结果行、`❄` spinner（海鸥振翅的轻盈）、`✔`/`✘` 状态 |
| **渐进披露** | 长输出折叠、尾部摘要、按需展开 | 工具输出默认显示尾部 3–5 行 + 总行数；diff 用彩色 patch 不贴全文 |
| **安静的成功** | 成功不庆祝，失败/需注意才提高视觉音量 | 测试通过一行海草绿；只有危险操作才用陶土红警示 |

### 8.4 关键界面元素规范

**启动 Banner**（首次进入时一次，之后不再打扰）：

```
  ☁ Glaucous · coding agent
  雨过天青，海鸥滑翔，代码自有清凉
```

**状态栏**（常驻底部，单行，信息让位给内容）：

```
[◆ plan | deepseek-chat | ctx 34% ███████░░░ 43k/128k]        ← Plan 徽标天青
[⬥ build·每次审批 | deepseek-chat | ctx 41% ████████░░ 52k/128k] ← Build 徽标亮青
```

占用条三档变色：低→海草绿；>70%→落日橙（附 `建议 /compact`）；>85%→陶土红（提示「🌊 即将自动压缩」）。

**工具调用行**（无框，学 Claude Code 密度）：

```
  ⏺ bash  pytest -q                          0.8s   ← ⏺ 天青，命令海鸥白
    ⎿ 12 passed in 1.2s                             ← 结果海盐青，仅尾部摘要
  ⏺ read  src/auth/session.py                 0.1s
    ⎿ 214 行                                        ← 行数即摘要
  ⏺ edit  src/auth/session.py ❄               —     ← spinner 表示进行中
```

**方案确认卡**（Plan→Build 切换，落日橙描边——需要人介入的时刻）：

```
╭─ ◆ 方案已就绪 ──────────────────────────────╮
│  目标 / 步骤摘要（最多 5 行）                 │
│  ① 开始构建，每次请求权限                     │
│  ② 开始构建，同意所有权限                     │
│  ③ 继续讨论一下                              │
╰────────────────────────────────────────────╯
```

**审批卡**（Build 写操作；破坏性命令换陶土红警示边 + 风险标注）：

```
╭─ ⚠ 需要您的确认 ───────────────────────────╮
│  命令: rm -rf ./dist                        │
│  风险: 不可逆删除 · 工作区内                 │
│  [a] 同意  [b] 同意同类型  [c] 拒绝(附理由)  │
╰────────────────────────────────────────────╯
```

**ask_user 提问卡**（海鸥意象）：

```
╭─ 🕊 请教你 ────────────────────────────────╮
│  未找到 JDK，请提供路径：                    │
│  [1] /usr/lib/jvm/java-8  [2] 帮我自动搜索   │
│  [3] 跳过此步                                │
╰────────────────────────────────────────────╯
```

**意象化交互文案**（图标保留意象，文字保持朴素——清凉是气质不是修辞）：

| 场景 | 文案 |
|---|---|
| 后台任务 | 「☁ 后台运行中」 |
| 上下文自动压缩 | 「🌊 上下文压缩中」 |
| 会话恢复 | 「🌅 已恢复上次会话」 |
| 错误重试 | 「↻ 重试中」 |

**思考/过程流**：思考内容海盐青斜体淡入淡出；完成汇报天青标题 + 海鸥白正文；正文流式 Markdown 内联渲染，不套面板。

### 8.5 终端兼容与降级

| 终端类型 | 处理 |
|---|---|
| truecolor（VS Code、Windows Terminal、kitty、Ghostty） | 完整 24bit 配色 |
| 256 色 | 映射到最近调色板 |
| 16 色（老旧终端） | 降级为加粗/反色，保底可读 |

**实现**：所有颜色走 `ui/theme.py` 单一出口定义色板常量（rich Theme），不散落硬编码；预留 `/theme` 切换暗/亮模式（亮模式 = 天青底 + 深字）。

## 13. 面试辩护要点（设计决策 Q&A 预案）

| 问题 | 回答要点 |
|---|---|
| 为什么 Plan/Build 两模式而不是三档权限？ | 两模式对应用户心智的两个阶段（想清楚→动手），权限档位内化为 Build 内的授权策略；概念减半、覆盖不变 |
| 为什么 Plan 模式在声明层隐藏写工具而不是执行层拦截？ | 源头治理优于事后拦截：模型看不到写工具就无从调用，省一轮失败交互、杜绝试探越权；执行层拦截仍保留作为纵深防御 |
| 选了"同意所有权限"为什么还有操作被拦？ | 用户授权语义是"构建本项目"，不可逆的区外访问与破坏性命令超出该语义；授权粒度与信任边界对齐 |
| 审批为什么是三选项？ | 同意=最细粒度，同意同类型=效率与安全的平衡，拒绝=控制权；覆盖授权决策完整谱系且认知负担最小 |
| glaucous.md 和 memory 为什么分两层？ | 规则（规范性）必须全量稳定生效，事实（经验性）可增删可淘汰；混存导致过时事实污染有效规则 |
| 为什么用原生 tool calling 而非 ReAct 文本协议？ | 结构化输出由 API 保证，解析面小更可靠；校验、容错、回喂全自研；文本协议保留 P1 兜底 |
| 界面为什么学 Claude Code？ | 它验证了"高密度 + 低噪音"是 agent 界面的最优解：无框优先让长过程可扫读，视觉音量只在需要人介入时升高；Glaucous 在此骨架上注入自己的色彩与意象 |
| 拒绝操作后为什么结构化回喂理由？ | 让模型理解"为什么被拒"并改道，而不是重试触发熔断；错误信息即控制信号 |
| skill 为什么惰性加载？ | 索引常驻（<30 token/个）保住触发召回，正文按需载入保住上下文预算 |
| 为什么压缩而非简单截断？ | 截断丢任务目标导致行为漂移；压缩保意图，且显式保留方案/任务清单作为执行锚点 |
| 为什么步数上限？ | 终止条件是 agent 的第一责任；上限是熔断器，正常任务远达不到 |
| 模型切换为什么能无缝接力？ | 上下文用 OpenAI 通用消息结构持久化，切换只改路由，不动历史 |
| 为什么不用框架（除题目禁止外）？ | 核心价值恰在 loop/上下文/权限/工具治理这层，框架把它藏起来就没法对设计负责 |

## 14. 风险与应对

| 风险 | 应对 |
|---|---|
| 时间不足 | §12 裁剪顺序明确；模式+权限+上下文+glaucous.md+基础主题为底线 |
| 命令分类器漏判危险命令 | 无法判定时保守升级走审批；正反例单测 |
| 记忆/规则注入污染上下文 | glaucous.md 全量但提示精简；事实条目上限 + 裁剪；自动提炼须确认 |
| 方案质量差导致 Build 返工 | 方案模板引导 + 用户"继续讨论"回路 + Build 中可回 Plan |
| 网关不支持 function calling | 文本协议 P1 兜底 |
| 演示翻车 | 评测集选稳定复现任务；视频允许剪辑；auto-approve 模式减少打断 |
| 上下文溢出 | 三级截断 + 占用条预警 + 预算守卫兜底 |
| 终端配色兼容 | theme.py 单一出口 + 256/16 色降级策略（§8.5） |
