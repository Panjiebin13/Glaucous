# Glaucous 产品路线图（v0.2 方向草案）

> 记录时间：2026-08-28（M2 验收完成后、M3 启动前）
> 状态：方向已定，排期待与 M3–M5 现有计划合并调整

## 一、产品定位（叙事主线）

**别的 coding agent 在比谁更自主，Glaucous 比谁更可信**——
「第一个把权限治理当核心能力的中文 coding agent」，最终目标是：**让 agent 可信地进入企业研发流程**。

现有积累即护城河：Plan/Build 双模式、三级风险分类、工作区沙箱、审批三选项、auto-approve 底线守卫、审计日志（M1 已验收）；上下文预算与压缩（M2 已验收）。

## 二、四个优化方向（按落地顺序）

### ① checkpoint 回退（约 1 天）—— 信任闭环

- **定位**：审批管"事前"，回退管"事后"，合起来才是完整可控闭环。企业采纳的安全感基石。
- **做法**：进入 Build 时打 checkpoint（git commit 或 `.glaucous/checkpoints/` 快照）；提供 `/rollback`；可探索审批拒绝触发自动回退。
- **验收形态**：演示"改坏了 → 一键回退"，一屏看懂。

### ② 内置 spec 流程（约 2–3 天）—— 差异化招牌

- **定位**：把团队已在实践的 SDD（需求 → spec → 评审阻塞归零 → 编码 → code 评审）产品化为 agent 能力：`/spec` 命令 = 需求 → 生成 spec → LLM 自评审循环 → 产出方案。agent 按"软件工程流程"干活，而非蛮力改代码。
- **已有地基**：submit_plan 落盘 `.glaucous/plans/`、read_plan 回读（M2）；docs/designs + docs/reviews 的完整实践模板。
- **窗口期**：spec-driven development 刚热起来，先发可占位。

### ③ 串行子 agent + 权限继承（约 2–3 天）—— 护城河加深

- **定位**：大仓多模块/并行修 bug 的企业刚需。**独到打法不是"有子 agent"（竞品已有），而是子 agent 继承权限管线**：父 agent 出方案，子 agent 在沙箱+审批约束下执行，审计日志记录归属。多 agent 权限治理目前无人做。
- **架构**：子 agent = 独立 AgentLoop 实例（隔离 History + 收窄工具注册表 + 受限权限），经 `spawn_agent` 工具调度；上下文隔离复用 M2 预算管线。
- **约束**：第一版只做串行子任务，规避并发审批交互噪音。

### ④ 长任务运行（不单独立项）—— 前三者的组装

- **判断**：长任务的本质是"状态恢复 + 中途纠偏"，单靠跑得久无意义。
- **组装公式**：长任务 = ② spec 拆任务清单 + ① 每任务 checkpoint + 已有 resume + 清单进度持久化后按清单续跑。
- **已有地基**：会话 JSONL + `--resume`（M0）、上下文压缩 L0/L1/L2（M2）、方案锚（M2）。

## 四、与早期定位讨论的合并结论

"安全可控企业级"与本路线是**同一条故事线的不同章节**：回退是安全的兜底，spec 是企业研发流程，子 agent 权限继承是治理延伸。对外统一叙事：**Glaucous = 让 agent 可信地进入企业研发流程的中文 coding agent**。
