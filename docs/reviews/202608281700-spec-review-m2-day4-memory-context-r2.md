## 建议（建议修复 / 可选优化）

- **[S-11] `compact_history` 签名参数 `plan_anchor` 与 S-05 归属描述未对齐** — spec §3（行 110 `compact_history(messages, llm, plan_anchor: str | None)`）vs §4.7（行 218「compactor 内部自 plans 目录构造锚段……loop 只注入 plans 目录路径」）/ §4.9（行 230 `plans_dir: Path`）。§4.7 已明确锚段构造归属 compactor、loop 只传目录，但 §3 签名参数名仍为 `plan_anchor: str | None`，语义究竟是「plans 目录路径」还是「预构造的锚段文本」未注明——按字面易被实现为 loop 预构造传入，与归属声明相悖。建议：签名改名 `plans_dir: Path | None` 并注明「compactor 内部解析构造锚段」，与 §4.7/§4.9 数据流闭环。
- **[S-12] 阈值常量「单一出口」与 compactor 段常量定义并存，导入方向未指明** — spec §3 budget 段（行 98 `level_of` 注释「阈值常量单一出口」）vs compactor 段（行 101-102 `L1_TRIM_RATIO = 0.70`、`L2_COMPACT_RATIO = 0.85` 物理列于 compactor.py 名下，注释仅称「与 budget 阈值共用常量」）。若两模块各自定义 70%/85%，即违反概设 §4.2「占用数据与截断策略共用同一套阈值常量」的单一出口意图。建议：一句注明「常量定义于 budget.py，compactor 导入」，或常量集中至 compactor 由 budget 导入——二选一，消除两处定义的歧义。
- **[S-13] 「轮」未精确定义，L1/L2 边界与配对断言均依赖它** — spec §3（行 103 `L1_KEEP_RECENT_ROUNDS = 2`）、§4.6/§4.7（「最近 K 轮」「早期段以完整轮为单位」，行 204/214）、§8（行 282「轮次完整性断言」）。REPL 多轮共享 history 且单次 run() 内含多个 assistant/tool 循环，「轮」=「一条 assistant(tool_calls) 及其全部配对 tool 消息」还是「一次 run()」未指明。这直接影响 L1 保留边界、L2 段切分与「配对合法性断言」的可实现性/可测试性（§9 债务项「最近 K 轮保留」「压缩后配对合法」均需此定义才能成测）。建议：以 assistant 消息为轮锚点（tool 消息归属其前 assistant）补一句定义。
- **[S-14] memory_save 去重的作用域范围未指明** — spec §4.2（行 172「重复内容去重：content 完全一致时刷新 last_used 而非新增」）。全局与项目两个存储文件，去重是作用域内比较还是跨作用域合并比较未说明（跨作用域去重会破坏双作用域隔离语义，FR-21/概设 §7.2）。建议注明「同作用域内去重」。
- **[S-15] L1 常驻锚行与概设 §5.2 锚定义的字面差异未声明取舍；目标提取规则模糊** — spec §4.7（行 216 锚行为「目标：……；任务 N 项」）。概设 §5.2 锚定义为「方案已就绪：.glaucous/plans/<id>.md（目标一行 + **未完成任务清单**）」——spec 常驻锚行只含任务数不含清单，任务清单改由 L2 锚段承载（行 218 已落实「解析……目标与任务清单」）。语义上「方案在哪、该做什么」已达（概设锚的核心目的），但字面差异宜一句话声明取舍理由（常驻成本），避免验收/答辩时被按字面对照。另「自方案全文提取首行目标」（行 216）规则含糊：方案全文首行通常是 markdown 标题而非目标语义，建议指明提取规则（如「目标：段落首行，无则首个非空行，提取失败省略」——行 216 已有失败省略兜底）。
- **[S-16]（可选）阈值配置承载形式的既存偏差提示** — spec §2/§6 以环境变量 `GLAUCOUS_CONTEXT_LIMIT`/`GLAUCOUS_MEMORY_TOP_N` 承载阈值，与概设 §3（配置 TOML）/§9（config.toml 含「截断阈值」）存在表述差异。此偏差自 Day1 基线延续（config.py 全量环境变量范式，概设 §9 亦列有环境变量条目），非本 spec 引入，实施沿现状无碍；建议 M3 若落地 config.toml 时将阈值迁入归位。
- **[S-17]（可选）plans id 同秒多方案的字典序边缘** — spec §4.7（行 216 `id=时间戳+随机后缀`）+ 行 218「resume 后按文件名字典序取最大」：同一秒内连续两次 submit_plan 时随机后缀使字典序与时间序可能不一致。概率极低、后果轻微（取到同秒内另一版方案且 read_plan 仍可达），可忽略；如要消除可将时间戳精度提至毫秒。
