## 一、阻塞问题

### B1. 配置错误提示与 Banner 存在动态内容未加 `markup=False`：段名被吞（必现）或启动报错路径崩溃（可复现）
- **维度**：Spec 符合性 + 逻辑正确性
- **代码位置**：
  1. `src/glaucous/cli.py:373` `renderer.console.print(f"配置错误：{exc}", style="glaucous.error")`（默认 `markup=True`）；
  2. `src/glaucous/ui/renderer.py:150` `self.console.print(f"当前模型：{self.model_name} · …", style="glaucous.muted")`（banner 第三行，`model_name` 为用户在 models.toml 自定的段名，默认 `markup=True`）。
- **spec 位置**：§8 风险表「rich markup 误解析代码/错误文本 | **全部动态内容 `markup=False`**」；§8「models.toml 写错导致启动失败 | 解析错误信息**指明段名/字段**」。
- **冲突/缺陷说明**（两处均经本机端到端复现）：
  - `registry.py` 的错误文案设计上必含段名（如 `档案 [a] 缺少字段：model/api_key_env`）。经 rich markup 解析，`[a]` 被当作样式标签**静默吞掉**——实测以缺字段的 `models.toml` 启动，用户看到的是 `配置错误：档案  缺少字段：model/api_key_env`，段名丢失，违反「错误信息指明段名」承诺（用户无法定位是哪个档案写错）；
  - 段名触发解析异常时直接崩溃：构造合法 TOML `[models."/"]`（缺字段），报错文案恰为 `档案 [/] 缺少字段：…`，启动时抛出未捕获的 `rich.errors.MarkupError: closing tag '[/]' at position 8 has nothing to close`（traceback 指向 `cli.py:373`），用户得到 MarkupError 堆栈而非配置错误提示——错误报告路径本身必现异常；
  - banner 第三行同理：档案名含 `[...]`（toml 引号键可做到）时启动 banner 即吞字或抛 MarkupError。
  - renderer 其余动态输出（note/info/error/tool 行/卡片正文/状态行）均已 `markup=False` 或经 `Text` 施加，仅此两处遗漏。
- **修复方向**：上述两处补 `markup=False`（或改经 `renderer.note`/`Text` 通道）；建议顺手全仓复查 `console.print(f"...")` 动态插值点（当前仅余此两处）。
