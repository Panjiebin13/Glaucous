## 〇、设计宗旨与三条主线

**宗旨：高自主、长任务运行、尽可能减少对人类的干扰。**

一个编程智能体的价值不在于「每步都问你」，而在于「交代清楚后能自己干完，干坏了能兜住」。围绕这个宗旨，Glaucous 的全部设计收敛为三条主线：

| 主线 | 问题 | 答案 |
|---|---|---|
| **主线一：长任务跑得动** | 大任务步骤多、上下文会膨胀、做着做着会跑偏 | Spec 详细计划 + 任务分解执行 + 子 agent 隔离 + 四级上下文预算工程 |
| **主线二：需求先说清** | 减少干扰的前提是需求明确，否则 agent 越自主错得越远 | /spec 澄清访谈 + Spec 书面契约 + /fork 分支讨论 + 全自动免批准 |
| **主线三：安全有兜底** | 高自主必须配高兜底，否则用户不敢放手 | Checkpoint 每轮快照可回退 + 四级权限矩阵 + 底线守卫 + 协议合法性保障 |

下文按「总体架构 → 核心引擎（赛事五项自研点）→ 三条主线 → 设计决策速查」展开。

### 1.2 一次任务的完整数据流

```
用户输入
  → repl 任务轮（受管轮壳：思考区启动 / 轮级状态重置）
    → AgentLoop.run(task)
      → ① 任务入口 checkpoint（Git 快照 + 上下文锚）
      → ② push_user 入史（JSONL 逐条落盘）
      → ③ 循环 {
           守卫：步数上限 / 上下文预算（L1 裁剪 → L2 压缩）
           → LLM 流式请求（声明层按模式过滤工具）
           → 无 tool_calls → 自然终止，终答入史
           → 有 tool_calls → 逐个 dispatch：
               模式校验 → 权限管线（免审/弹卡/拒绝联动回退）
               → 参数解析（连续失败熔断）→ 本地执行
               → 超长输出 L0 截断落盘 → push_tool 回喂
         }
  → 轮末：思考区收缩为一行 + 终答 🕊 Markdown 卡片 + 用量行
  → 会话索引刷新（名称/条数/token 累计）
```

## 二、核心引擎：赛事要求的五项自研逻辑

赛事明确要求「重要逻辑需自行编写」的五项，逐一对应如下。

### 2.1 对话历史与上下文管理

**实现**（`context/history.py` + `budget.py` + `compactor.py`）：

- **持久化**：History 以 JSONL 逐条追加（首行 session_meta），进程崩溃最多丢最后一条；`--resume` 与 /resume 从文件重建内存视图；
- **协议合法性**：`view()` 输出 OpenAI 消息序列，方案/Spec 全文经视图变换替换为轻量锚（全文落盘可回读），避免长文档常驻上下文；
- **四级预算工程**（长任务的命脉，概设 §4.2）：
  - **L0 输出截断**：单条工具输出超 300 行 / 50KB → 截断入史 + 完整落盘 `.glaucous/outputs/<call_id>.log`，`read_output` 工具按段回取——上下文不被单次大输出击穿，信息不丢失；
  - **L1 本地裁剪**（>70% 水位触发，幂等）：保留最近 2 轮，更早的 tool 结果正文替换为本地派生摘要（首行+行数），零模型开销；
  - **L2 模型压缩**（>85% 水位追加）：调模型把早期轮次压缩为「会话阶段摘要」；连续失败 2 次自动降级加深 L1 并终止重试（防压缩调用空转循环）；
  - **预算耗尽优雅终止**（≥100%）：诊断提示「可 /exit 后 --resume 继续」，不硬崩；
- **用量可视**：状态栏 `○ N k/128k tokens` 实时占用环，/context 三档（128K/512K/1M）运行时可调。

### 2.2 工具的定义与本地执行

**实现**（`tools/base.py`）：

- **声明即代码**：每个工具是一个 `Tool` 子类——`name` / `description` / `parameters`（JSON Schema）/ `risk` / `modes` / `build_approval()` / `execute()`；`tool_schemas(mode)` 按当前模式过滤后发给模型（声明层）；
- **派发管线**（`dispatch`）：模式校验 → 权限管线（工具可基于参数构造审批动作）→ 参数解析与校验 → `execute` 本地执行 → 记账；
- **14 个工具全部本地执行**：文件读/写/编辑、目录浏览、grep 搜索、bash、ask_user、submit_plan、read_plan、memory 读写、load_skill、read_output、spawn_agent、read_spec——不依赖任何服务端托管工具（Code Interpreter / Files API 均未使用）；
- **写工具自带 diff**：write/edit 审批时携带 unified diff 供用户判断。

### 2.3 模型输出的解析

**实现**（`llm/client.py` + `tools/base.py`）：

- **流式 tool-call 拼装**：SSE delta 的 `tool_calls` 按 `index` 分桶累积 id/name/arguments 碎片，流结束后 `json.loads` 反序列化——这是自研的（SDK 不代管拼装语义）；
- **网关兼容降级**：`stream_options` 不被网关支持时自动去参重试一次；
- **解析熔断**：工具参数 JSON 解析连续失败 3 次 → 抛 `ParseCircuitBroken` 终止本轮（防「模型反复输出坏 JSON」死循环）；审批拦截不计入熔断计数；
- **善后保障**：终止/异常时为悬空 call_id 补推 ok=False 的 tool 消息（见 2.5）。

### 2.4 循环终止条件

**实现**（`agent/loop.py`，守卫固定在每次请求 LLM 之前）：

1. **自然终止**：响应无 tool_calls → 终答入史返回；
2. **步数上限**：默认 50 步硬熔断，防死循环；
3. **解析熔断**：连续 3 次解析失败（见 2.3）；
4. **预算耗尽**：压缩后仍 ≥100% 上下文上限（见 2.1）。

所有非自然终止都经 `diagnostic` 事件必达交付诊断文本（不依赖返回值推断，多步轮中间有流式输出时尤为关键）。

### 2.5 错误处理

- **协议合法性兜底（最隐蔽也最致命）**：OpenAI 协议要求每个 `assistant.tool_calls` 必须有配对 tool 消息，一旦悬空，共享历史的后续每轮请求都会被 API 400 拒绝、会话静默报废。loop 在**任何异常路径**（含 KeyboardInterrupt）都先 `_salvage_dangling_calls` 补推 ok=False 再上抛；
- **网络层**：可重试错误（429/5xx/超时）指数退避 + 随机抖动（1/2/4/8s，最多 4 次），4xx 不重试直接失败，重试状态实时通知界面（「↻ 重试中 · 第 N 次」）；
- **工具层**：单工具异常 → ok=False 回喂给模型自行调整（不终止轮）；
- **设施层**：索引写入 / checkpoint 创建等辅助设施失败一律「尽力而为 + 一次性告警」，不阻断对话主流程。

## 三、主线一：长任务如何跑得动

### 3.1 Spec：把大任务变成详细计划（FR-52~59）

大任务一次性丢给模型，结果是发散、越界、遗忘。Glaucous 的答案是 **Spec 子系统**——大任务先产出书面规格，再按规格执行：

```
/spec <需求>
 → 澄清访谈（ask_user 逐点澄清：目标边界/输入输出/约束/验收预期）
 → 用户确认「需求已清楚」
 → 起草：七节文档落盘 .glaucous/specs/<id>.md
   （需求与边界/澄清记录/约束/设计/任务清单/验收标准/风险与回退）
 → Spec 评审循环（≤3 轮）：评审子 agent 按检查清单出具报告
   （阻塞/建议分级），不通过则主 agent 修订；支持全自动/深度介入
 → 批准（全自动且无阻塞 → 免批准直接执行）
 → 执行管线：逐任务执行（见 3.2）
 → 代码评审循环（≤3 轮）：子 agent 对照「验收标准 + diff」评审
 → 验收核验：逐条 ✓/✗，全过 → verified；有未决 → archived 留痕
```

**状态机**：`draft → reviewing → approved → executing → code_review → verified/archived`，强校验迁移、frontmatter 落盘、中断可 `/spec` 续跑。

**为什么评审用子 agent**：评审需要「新鲜视角 + 完整规格上下文」；主 agent 自评审存在确认偏置，且评审的探索过程会污染主上下文。子 agent 隔离同时解决两者。

### 3.2 任务分解执行：小步约束

执行阶段不是一次性放羊，而是**逐任务受控推进**：

- 每个任务是独立一轮，任务消息三段式：**唯一小目标 + Spec 锚行（可 read_spec 回读全文）+ 「仅完成本任务，不越界」显式约束**；
- 每任务动手前打**权威任务级 checkpoint**（/rollback 可精确回到该任务前）；
- 任务成功 → checkbox 写回 Spec 文档（状态即文档，中断续跑不丢进度）；
- 任务失败 → 弹卡三选（重试/跳过/归档中止），失败域收敛在单任务。

### 3.3 子 agent 隔离：主上下文不膨胀（FR-60~64）

`spawn_agent` 工具派发子任务，`SubagentRunner` 保证完全隔离：

- **独立**：子 History（落盘 `.glaucous/agents/`）、子 system prompt、SessionState 快照复制、工具集 = 父集 − spawn_agent（防嵌套，声明层+执行层双保险）；
- **串行**：父派发后 await 到报告返回才继续（FR-64）；
- **回传纪律**：子过程不占父上下文，父史只增 2 条消息；报告 ≤1000 字四段式（摘要/修改清单/验证/风险），超限完整报告落盘 `outputs/` 可 `read_output` 回取——**信息不丢 + 上下文不污染**；
- **权限独立弹卡**：子 agent 遇审批独立弹窗并标注归属（🕊 子 agent 任务摘要），不汇总回父。

### 3.4 上下文工程：长任务不爆上下文

见 2.1 四级预算工程。配合 Spec 锚（规格全文不常驻）与子 agent 隔离，实测 20+ 轮、数万 token 的长任务占用稳定在低水位。

## 四、主线二：需求先说清（减少干扰的前提）

### 4.1 澄清访谈（FR-53）

`/spec` 入口强制先澄清：模型用 `ask_user` 逐点访谈（箭头选择卡），**用户确认「清楚」后才允许起草**——把方向分歧消灭在动手前，而不是执行到一半弹一堆卡。普通对话同样受「先澄清后开发」system prompt 软约束（FR-37）。

### 4.2 Spec 书面契约

澄清结论固化成落盘文档：做什么/**明确不做什么**/约束/验收标准。它是后续所有环节的唯一基准——评审审它、执行照着它、验收对着它核验。方向从「对话里的模糊共识」变成「可对照的书面契约」。

### 4.3 /fork：需求不清先讨论（FR-48）

`/fork` 复制当前会话另起分支（另存为语义，原会话不动）。用途：对方案有顾虑时先 fork 出一个分支与 agent 充分讨论/试跑，确认后再回原会话执行——**讨论的污染留在分支里，主会话保持干净**。会话管理全家桶（用户级存储 + 侧边索引 + `/sessions` 跨项目列表切换 + `/rename` + `/stats`）支撑长任务跨会话续接。

### 4.4 全自动 = 少弹卡

- **默认 Build + auto-approve**：启动即干活，不为「模式选择」打扰用户；
- **全自动 + 评审无阻塞 → 跳过批准卡直接执行**（用户决策 2026-08-31）；
- **git 兜底区放宽**：工作区是 Git 仓库时，区内文件写免审、区内危险命令降级为可豁免——「有兜底的地方不拦，没兜底的地方才拦」；
- 真正需要人的只有三处：需求澄清、方向批准（深度介入时）、无兜底的危险操作。

## 五、主线三：安全兜底（敢放手的前提）

### 5.1 Checkpoint：每轮快照，一键回退（FR-40~43）

**实现**（`checkpoint/`，纯 Git 子进程，零新依赖）：

- **快照机制**：每轮任务入口自动打快照。用**临时索引五步法**（`GIT_INDEX_FILE=临时索引` → read-tree → add -A → rm --cached 排除 .glaucous → write-tree → commit-tree → update-ref 到 `refs/glaucous/checkpoints/<seq>`）——不碰用户工作树与真实索引、不污染 stash 列表，且**能捕获 untracked 新增文件**（`git stash create` 做不到，这是对概设方案的显式修正）；
- **保留策略**：最近 50 个（`GLAUCOUS_CHECKPOINT_MAX_KEEP` 可配），超出自动淘汰最旧；
- **`/rollback`**：箭头选择历史快照 → 变更清单确认卡 → 文件精确还原（M 还原 / D 恢复 / A 移除）+ 可选「同时回退对话上下文」（锚配对校验，防错位截断）；
- **拒绝联动回退**（FR-43）：审批卡第四选项「拒绝并回退」——发现 agent 已经做坏时，拒绝的同时把文件退回到本轮任务前；
- **任务级快照**：Spec 执行期每任务前打权威快照，/rollback 可精确回到「该任务前」。

### 5.2 权限矩阵：四级定级与「为什么这么设」

**三级风险**（SAFE / WRITE / DANGEROUS）× **两种策略**（auto-approve / per-action），判定来自三处：

| 判定层 | 机制 |
|---|---|
| 路径沙箱 | `Workspace`：realpath 规范化 + 前缀校验（防 `../` 穿越与符号链接逃逸）；区外可审批不硬拒 |
| 命令分类器 | 首词白名单（只读命令）+ 危险模式表（`rm -rf /`、`sudo`、`curl\|sh`…）+ 复合命令/管道**逐段独立定级取最坏**（防 `echo a; rm -rf /` 被白名单遮蔽）+ 引号感知不误报 + 无法判定保守升级 |
| 工具自报 | 写工具基于参数构造审批动作（携带 diff） |

**当前矩阵**（2026-08-31 用户决策，git 兜底区）：

| 操作 | 定级 | 理由 |
|---|---|---|
| 区内读（含 .glaucous/ 日志） | 放行 | 读无完整性风险 |
| **区内文件写**（Git 仓库） | **免审** | checkpoint 可回退 |
| **区内危险命令**（rm/reset --hard 等，目标区内） | **WRITE（可豁免）** | 可回退，但删除不可逆于用户认知，留一次确认 |
| `.glaucous/` 写 | DANGEROUS 恒拦 | 快照刻意排除该目录（无 git 保证）+ 审计防篡改是底线 |
| 区外读 | WRITE（可同类型豁免） | 读取环境配置是真实需求（FR-13），但要可见 |
| 区外写 | DANGEROUS 不可豁免 | 无快照兜底 |
| `git push --force` / `sudo` / `curl\|sh` | DANGEROUS 恒拦 | 远端/系统侧影响，本地兜不住 |

**设计逻辑一句话**：放行与否不看「操作看起来吓不吓人」，看「**有没有兜底**」——有 checkpoint 兜底的尽可能放开（高自主），没兜底的（区外、运行时目录、远端）坚决拦住（可信）。

### 5.3 底线守卫

- **Plan 模式只读**：写工具在声明层就不发给模型，执行层二次拦截（双保险）；
- **DANGEROUS 永不被 auto-approve/批量豁免越过**（守卫优先级）；
- **模式快照**：每轮请求前取模式快照，声明层与执行层同轮一致，消除切换窗口期的不一致。

## 七、关键设计决策速查（面试辩护底稿）

| # | 决策 | 理由 | 拒绝的替代方案 |
|---|---|---|---|
| D1 | 默认 Build + auto-approve，安全靠兜底设施而非审批 | 高自主是宗旨；审批只拦得住「看到的」，兜底才兜得住「发生的」 | 默认 per-action（每步弹卡，长任务不可用） |
| D2 | 评审用子 agent、执行用主 agent | 评审需新鲜视角+隔离；执行需简单可控 | 主 agent 自评审（确认偏置+上下文污染） |
| D3 | Spec 一等公民（独立状态机/落盘/命令面），不是 Plan 附属 | 大任务需要可追溯的书面契约与双评审 | Spec 作为 Plan 的加长版（无生命周期管理） |
| D4 | 快照用临时索引五步法而非 `git stash create` | stash create 无法捕获 untracked，「新增文件移除」验收点会落空 | stash 方案（概设原案，实测不成立后显式修正） |
| D5 | 权限按「有无兜底」划分而非「操作类型」 | 有 checkpoint 的区内写放开才有高自主；区外/远端无兜底必须拦 | 一刀切严格（退化为低自主）/一刀切放开（不可信） |
| D6 | 子 agent 串行、报告 ≤1000 字+落盘回取 | 并行复杂度高收益低；报告限额保父上下文，落盘保信息不丢 | 并行子 agent（v2 增强）/全文回传（上下文膨胀） |
| D7 | 对话历史 JSONL 逐条落盘 + 视图变换做锚替换 | 崩溃最多丢一条；长文档不常驻上下文但可回读 | 全内存（崩溃全丢）/全文常驻（上下文爆炸） |
| D8 | 循环守卫前置（每次请求 LLM 前评估终止条件） | 无论循环从哪条路径回来都会重新评估，无漏网路径 | 仅入口检查（异常路径绕过） |
| D9 | 悬空 tool_call 强制善后 | 协议非法会让会话静默报废，比任何单轮失败都致命 | 直接抛出（会话报废） |
| D10 | 验收保守口径（全 ✓ 且无 ✗ 才 verified） | 宁可归档留痕，不可把未达标包装成通过 | 无 ✗ 即通过（契约违约时误判） |

## 八、工程成熟度（可答辩的事实）

- **代码规模**：约 1.2 万行 Python（src + tests），38 个测试文件、**336 passed**；
- **开发方法**：Spec 驱动交付——每个里程碑先出 spec 约束文档，经 spec-reviewer 子代理评审循环（多轮修复至通过）再编码，编码后经 code-reviewer 子代理评审循环；全部评审报告留痕 `docs/reviews/`（40+ 份）；
- **文档链**：需求文档（64 条 FR）→ 概要设计 → 里程碑 spec（8 份）→ 评审报告 → 代码，需求可逐条追溯；
- **提交历史**：一任务一提交、中文提交信息、完整历史未压缩改写。
