- 版本：v5.0（2026-08-29），对应产品 v1.1
- 前序版本：[编程智能体概要设计说明书.md](编程智能体概要设计说明书.md)（v4.1，对应产品 v1.0）——本文描述 v1.1 增量设计；未提及的 v1.0 设计（LLM 网关、记忆系统、上下文三级压缩、Glaucous 主题等）继续有效
- 关联文档：[编程智能体需求文档v1.1.md](编程智能体需求文档v1.1.md)（FR-35~64）
- 定位更新：*「雨过天青，海鸥滑翔，代码自有清凉」*——现在是**高自动化、面向长任务**的清凉 agent：启动即干（Build 默认），先澄清后动手，大任务走 Spec 流程，评审交给子 agent，改坏了一键回退。

## 1. 项目概述

### 1.1 设计目标（v1.1 修订）

1. **高自动化**：默认 Build + auto-approve，能直接干就直接干，审批卡只在底线时刻出现。
2. **可信兜底**：高自动化的风险由 checkpoint 回退 + 工作区沙箱 + 底线守卫 + 审计日志四层兜底，防超出规模的破坏。
3. **工程化干活**：大任务不蛮力——Spec 流程（澄清→起草→评审→执行→代码评审→验收）把软件工程实践产品化，这是与 Codex/Claude Code 的核心差异（两者的 spec 均为外置 Issue 或社区 skill，非产品内置）。
4. **长任务支撑**：会话管理增强（用户级存储/索引/命名/分叉/统计）+ Spec 任务清单锚点 + checkpoint，长任务可跨会话续接、可回退。
5. **上下文纪律**：评审用子 agent（隔离上下文），Spec 轻量锚注入（不常驻全文），延续 v1.0「方案锚」思想。

### 1.2 非目标（v1.1 修订）

v1.0 声明的非目标中，**「多 agent 协作」在本版本部分解除**——支持**串行子 agent**（spawn_agent，无嵌套）；并行编排、agent 树仍然不做。多模态、Web/GUI、模型训练/微调、IDE 插件维持不做。

## 2. 总体架构

### 2.1 分层架构图（v1.1）

```
┌──────────────────────────────────────────────────────────────────────┐
│  CLI 交互层   REPL / 流式渲染 / Glaucous 主题 / 卡片（审批·提问·方案    │
│              ·Spec 评审报告·回退确认·会话列表）/ 状态栏                 │
├──────────────────────────────────────────────────────────────────────┤
│  Agent 编排层  loop / state / guard / 模式状态机（Build 默认·Plan 研究）│
│               ┌────────────────────────────────────────────┐         │
│               │  多 Agent 模块  spawn_agent 工具            │         │
│               │  子 AgentLoop（隔离 History/预算/工具集）    │         │
│               └────────────────────────────────────────────┘         │
├──────────┬──────────┬───────────┬───────────┬────────────────────────┤
│ 上下文管理 │  工具系统 │  权限体系   │ Spec 子系统 │ Checkpoint 模块        │
│ history  │ registry │ workspace │ 状态机     │ Git 快照 / refs         │
│ budget   │ executor │ 底线守卫   │ 双评审循环  │ /rollback / 保留策略    │
│ compactor│ (含子集)  │ approval  │ 任务清单执行│                        │
├──────────┴──────────┴───────────┴───────────┴────────────────────────┤
│  会话管理子系统   ~/.glaucous/sessions/<project-hash>/ + session_index │
├──────────────────────────────────────────────────────────────────────┤
│  本地执行环境    文件系统 / shell 子进程(asyncio) / git 子进程          │
└──────────────────────────────────────────────────────────────────────┘
```

新增模块相互依赖关系：Spec 子系统依赖多 Agent 模块（评审循环）与 Checkpoint 模块（任务级检查点）；Checkpoint 与会话管理相互独立；多 Agent 模块仅依赖既有 loop/tools/permission 接口。

### 2.2 核心工作流（v1.1）

```
启动 → Build 模式（auto-approve + 底线守卫）
用户输入需求
  → 澄清：需求含糊则 ask_user 明确边界（提示词软约束）
  → 规模判断：
      ├─ 小任务：简述做法 → 直接执行（写操作静默/底线审批）
      │          高风险 → 主动出方案确认卡（submit_plan 保留语义）→ 批准后执行
      └─ 大任务：建议 /spec → 用户确认 → 澄清访谈 → 用户确认需求清楚
           → 起草 Spec（.glaucous/specs/<id>.md，状态 draft）
           → Spec 评审循环（评审子 agent，≤3 轮，全自动/深度介入）
           → 用户批准（approved）
           → 主 agent 按任务清单逐项执行（executing，每任务 checkpoint）
           → 代码评审循环（评审子 agent 对照验收标准与 diff，≤3 轮）
           → 验收报告 → verified/archived
用户随时：/plan 研究 · /rollback 回退 · /sessions 换会话 · /stats 统计
```

## 3. 技术选型增补

| 项 | 选择 | 理由 |
|---|---|---|
| Checkpoint 存储 | Git 命令（子进程调用），自定义 refs 命名空间 | 工作区本就有 Git；`git stash create` + `git update-ref refs/glaucous/checkpoints/<n>` 生成快照对象——不动用户工作树、不污染 stash 列表、对象有 ref 引用不被 gc；零新依赖 |
| 会话索引 | 侧边 JSON（session_index.json） | 列表秒回、可从 JSONL 重建；SQLite 对当前体量过重 |
| project-hash | `sha1(workspace 绝对路径)[:12]` | 稳定、无路径长度问题；meta 内保存原路径用于展示 |
| 会话存储 | `~/.glaucous/sessions/<project-hash>/` | 对齐 Claude Code（~/.claude/projects/<hash>/）与 OpenCode（集中存储）的主流做法；跨项目浏览的前提 |

## 4. 核心引擎设计变更

### 4.1 模式状态机重构（FR-35/36/39）

```
状态：BUILD（默认） | PLAN（研究）
启动 → BUILD；/plan → PLAN；/build 或用户口头确认 → BUILD
```

| | BUILD（默认） | PLAN（研究模式） |
|---|---|---|
| 语义 | 执行与修改 | 只读研究与方案讨论 |
| 工具 | 全部（spawn_agent 仅主 agent） | 写工具声明层隐藏（复用 v1.0 机制）；bash 仅 SAFE 白名单 |
| 写操作 | 按授权策略（默认 auto-approve + 底线守卫） | 不存在 |
| 产出 | 代码修改、命令结果 | 分析结论与建议（对话形式） |

- **v1.0 机制复用**：声明层隐藏（写工具不出现在 tools 定义）、bash SAFE 白名单、工作区沙箱、危险级别分类全部原样保留。
- **授权策略**：`POLICY_AUTO_APPROVE` 为默认值；底线守卫（区外访问 + DANGEROUS 永远单独确认）逻辑不变，只是从「auto-approve 例外」变为「默认策略的固有行为」。per-action 保留为用户可选（`/build per-action` 或 config）。
- **守卫检查点**：五类终止条件与「请求 LLM 前过守卫」的检查点位置不变。

### 4.2 高风险主动确认（FR-38）

- `submit_plan` 工具保留，语义从「Plan 模式的出口协议」变为「主 agent 主动请求确认」：高风险任务（大范围重构/删除/改配置/涉及 `.glaucous/` 与规则文件）时，主 agent 产出方案卡 → 用户 `[a] 批准执行 / [c] 修改意见` → 批准后在当前 Build 策略下执行。
- 触发判断由提示词引导（风险特征清单写入 BASE_PROMPT），不做硬编码规则——误判成本低（多确认一次），漏判兜底有审批与 checkpoint。

### 4.3 先澄清后开发（FR-37）

BASE_PROMPT 增补段落（要点）：
1. 动手前必须明确需求边界：改哪些文件、期望行为、有无隐含约束；含糊先 `ask_user`。
2. 小任务简述做法（2~3 句）即可动手；大任务建议用户 `/spec`。
3. 禁止在需求未澄清时启动长流程（spec 起草/评审）。

软约束起步；评测「模糊需求」用例不达标时升级为机制加固（首轮写操作前一次性提示，预留在 §13 风险表）。

### 4.4 子 agent 的上下文纪律（FR-61/63）

- 子 agent 全程不触碰父 History：父 agent 视角里只有一次 `spawn_agent` 调用与其 ToolResult（最终报告）。
- 子 agent 的中间过程经自身 on_event 渲染（UI 可见、可折叠），不回传。
- 报告规范（工具结果文本，≤400 字）：`任务结果摘要 / 修改文件清单 / 验证结果 / 风险与遗留`。

## 5. Checkpoint 模块（FR-40~43）

### 5.1 Git 快照机制

```
创建（每轮 run() 开始前）：
  commit = git stash create "glaucous-checkpoint"     # 生成快照对象，不动工作树
  git update-ref refs/glaucous/checkpoints/<seq> <commit>
  # 不 store 进 stash 列表 → 不污染用户 stash；refs/glaucous/* 命名空间不被 gc
  元数据写入 .glaucous/checkpoints.json（seq、时间、任务摘要、commit hash）

回退（/rollback）：
  1. 列出保留期内 checkpoints（时间 + 任务摘要），用户选择
  2. 计算将变更文件清单：git diff --name-status <当前> <目标 ref>
     ├─ 修改/删除的文件 → 还原
     └─ checkpoint 之后新增的文件 → 列入"将移除"清单
  3. 回退确认卡（含变更清单）→ 确认后：
     git restore --source <ref> --worktree --staged -- .
     + 按清单移除新增文件
  4. 默认保留对话上下文；「同时回退上下文」= 截断 History 至该 checkpoint 对应轮次前
     （JSONL 同步截断，配对校验复用 load 的修复逻辑）
```

### 5.2 关键语义

| 项 | 设计 |
|---|---|
| 粒度 | 每轮用户任务一个 checkpoint（run() 入口处）；Spec 任务清单额外每任务一个（复用同机制，任务摘要标注任务号） |
| 保留 | 最近 50 个（`config.checkpoint_max_keep`，可配）；超出删除最旧 ref（`git update-ref -d`）+ 清理索引行 |
| 非 Git 工作区 | 创建时检测 `git rev-parse --is-inside-work-tree` 失败 → 提示「当前工作区不是 Git 仓库，checkpoint 不可用」，不自动 init；该场景下 /rollback 与审批拒绝回退降级为不可用提示 |
| 拒绝联动（FR-43） | 审批卡在拒绝分支增加「拒绝并回退」选项：回退到本轮任务入口 checkpoint，回喂「用户拒绝并已回退：{理由}」 |
| 审计 | 每次 create/rollback 写 audit.log（`event: checkpoint_create / rollback`） |
| 性能 | `git stash create` 仅对已跟踪文件变更生成快照（untracked 经 `--include-untracked` 语义由 stash create 处理）；大仓 O(变更文件数)，非全仓扫描 |

## 6. 会话管理子系统（FR-44~51）

### 6.1 存储布局与索引数据模型

```
~/.glaucous/
├── sessions/<project-hash>/<timestamp>-<rand>.jsonl   # 会话文件（v1.0 格式不变）
└── session_index.json                                  # 侧边索引

# session_index.json
{ "version": 1,
  "projects": {
    "<project-hash>": {
      "workspace": "/home/u/proj",
      "sessions": [ { "id", "name", "created_at", "updated_at",
                      "message_count", "token_used", "status" } ] } } }
```

- **索引写入时机**：会话创建、/rename、/fork、会话结束（updated_at/message_count/token 刷新）；追加失败不阻断对话（与 v1.0 持久化「尽力而为」一致）。
- **重建**：索引缺失/JSON 损坏 → 遍历所有 project-hash 目录读各 JSONL 首行 meta + 尾部统计重建（降级路径明确）。
- **token_used**：取 budget 记账器会话累计值，结束时刻快照。

### 6.2 命令面

| 命令 | 语义 |
|---|---|
| `/sessions` | 列表卡：默认当前项目，`[a]` 切全部项目；行 = 名称/更新时间（相对）/消息数/token |
| `/sessions <kw>` | 名称模糊搜索（跨项目） |
| `/sessions <id>` | 切换会话（恢复流程复用 resume_history） |
| `/rename <name>` | 重命名当前会话，同步索引 |
| `/fork <name>` | 复制当前全部历史 → 新会话文件 + 索引登记（另存为语义，从当前状态分叉） |
| `/stats` | 统计卡：当前会话（消息数按角色分布/token/活跃时长/审批决策分布——后两者经 audit.log 汇总）+ 全局聚合 |

- **切换保护（FR-50）**：Build 中（loop 运行中）拒绝切换并提示；空闲时切换仅恢复对话；恢复后检测 `git status` 有未提交修改 → 提示「工作区有未提交修改（可能来自其他会话），可 /rollback 或 git status 检查」。
- **自动迁移（FR-51）**：启动时扫描 `<workspace>/.glaucous/sessions/*.jsonl` → 移动到用户级 project-hash 目录 → 更新索引 → 原目录留空（一次性迁移，打日志）。

## 7. Spec 子系统（FR-52~59）

### 7.1 状态机

```
draft → reviewing → approved → executing → code_review → verified
                        │            │            │
                        └──────(修订回环 ≤3 轮)────┘→ archived（任何阶段可归档终止）
```

### 7.2 Spec 文档结构（.glaucous/specs/<id>.md）

```markdown
---
id: spec-20260829-143022
name: 用户认证模块
status: executing          # draft/reviewing/approved/executing/code_review/verified/archived
created_at / approved_at / round: N
---
## 需求与边界        ## 澄清记录（访谈问答）
## 约束              ## 设计
## 任务清单（checkbox，执行进度直接勾选在文档上）
## 验收标准（结构化：每条可验证，附验证方式）
## 风险与回退
```

### 7.3 双评审循环（评审子 agent 承担，FR-55/57）

```
Spec 评审循环（≤3 轮）：
  spawn_agent(role=评审员, 输入=Spec 全文 + 检查清单 + 用户本轮反馈)
  → 评审报告：{ 通过: bool, 阻塞级问题[], 建议级问题[] }
  → 未通过：主 agent 修订 → 下一轮；深度介入模式每轮报告后等用户建议再继续
  → 通过 或 3 轮耗尽 → 呈现 Spec → 用户批准（approved）/ 继续修改

代码评审循环（≤3 轮，执行完成后）：
  spawn_agent(role=代码评审员, 输入=Spec 验收标准 + git diff（自任务入口 checkpoint）+ 评审清单)
  → 评审发现 → 主 agent 修复 → 复审
  → 通过 → 验收报告（对照验收标准逐项核验）→ verified；否则 archived 附未决问题
```

**评审检查清单**（内置模板，system prompt 注入评审子 agent）：
- Spec 评审：需求边界完整？验收标准可验证？任务清单覆盖需求且粒度合理？约束无冲突？风险与回退已识别？
- 代码评审：逐条对照验收标准？diff 是否越出任务边界？是否违反 Spec 约束（如禁改目录）？测试覆盖？

**为何评审用子 agent**：评审需要「新鲜视角 + 完整 Spec 上下文」，若在主 agent 上下文内自评审，模型对自己刚写的内容存在确认偏置，且评审过程会污染主上下文。子 agent 隔离解决两者（呼应面试辩护点）。

### 7.4 执行管线（FR-56）

- 批准后 Spec 锚注入主 agent 上下文（`Spec 已就绪：.glaucous/specs/<id>.md（目标一行 + 未完成任务清单）`），注册 `read_spec` 工具按需回读全文——与 v1.0 方案锚同款机制。
- 任务清单与 todo_write 联动：任务进度勾选直接写回 Spec 文档 checkbox（状态即文档）。
- 每任务开始前打任务级 checkpoint（§5.2）；任务失败可 /rollback 到该任务前。
- 全部任务完成 → 进入代码评审循环。

### 7.5 命令与管理面

`/spec [需求]`（发起；无参且存在执行中 Spec 则显示进度）、`/specs`（列表 + 状态）、`/spec status`（当前 Spec 任务勾选 + 验收核验结果）、`/spec cancel`（终止并归档）。Spec 卡片（评审报告卡/批准卡/验收卡）遵循「人介入时刻才升格 Panel」的 v1.0 布局原则。

## 8. 多 Agent 模块（FR-60~64）

### 8.1 spawn_agent 工具契约

```python
# tools/spawn_agent.py（仅注册给主 agent）
参数: task: str（子任务描述，含完成标准）
      context: str = ""（补充上下文：相关文件、约束、父任务背景）
行为: 构造子 AgentLoop → 同步 await 子 loop.run(task) → 返回结构化报告文本
风险: SAFE（派发本身无副作用；子 agent 内部的写操作按 FR-62 审批）
```

### 8.2 子 AgentLoop 生命周期

```
构造：
  History.create(sub_system_prompt, workspace)   # 独立会话文件（.glaucous/agents/ 目录，不进会话索引）
  system prompt = 子任务角色 + 工作区信息 + glaucous.md 规则 + 任务描述
                  （不注入记忆/skill 索引——评审员需要的是任务上下文，不是主 agent 的全部包袱）
  ToolRegistry = 父 registry 的子集（去掉 spawn_agent）→ 防嵌套
  SessionState = 独立实例，授权策略 = 复制父当前值
  budget = 独立记账（max_steps 沿用 config，token 预算独立）
执行：父 dispatch spawn_agent 时 await（串行，FR-64）；on_event 独立渲染通道（前缀标注子 agent 身份）
终结：终答文本 = 结构化报告 → ToolResult 回传 → 子会话文件保留（可追溯），审计记录归属
```

### 8.3 权限继承与审批（FR-62）

- 子 agent 共用 ApprovalPipeline 构造逻辑但持独立 SessionState：auto-approve 继承 → 子 agent 写操作静默；per-action 继承 → 子 agent 独立弹卡，卡片标题标注 `🕊 子 agent（任务：{父任务摘要}）`。
- 底线守卫无差别生效（区外/破坏性永远确认）；audit.log 每条记录增加 `agent` 字段（`main` / `child-1`）。
- 子 agent 的 ask_user 直接透传给用户（评审子 agent 不应 ask_user，其输入已含全部材料——检查清单约束写入评审员角色提示词）。

## 13. 风险与应对

| 风险 | 应对 |
|---|---|
| 默认 Build 下模型「不澄清就蛮干」 | 提示词软约束 + 模糊需求评测用例；不达标升级为「首轮写操作前一次性提示」机制（预研半天） |
| git stash create 在大仓/大量 untracked 下慢 | 限时 + 超时跳过本轮 checkpoint 并提示；只对变更集生成快照 |
| 用户对 /rollback 还原预期不符（新增文件被移除） | 回退确认卡显式列「将移除」清单；未确认不动手 |
| 子 agent 审批打断过频（per-action 继承时） | 评审类子任务输入完备不该有写操作；执行类子任务建议在 auto-approve 下使用（提示词引导） |
| Spec 评审循环空转（3 轮不过） | 轮次耗尽强制升级给用户裁决（继续修/归档终止），不无限循环 |
| 会话索引与实际文件漂移 | 索引只做加速，列表以 JSONL 为准校验；损坏即重建 |
| 评审子 agent 产出幻觉问题清单 | 评审报告要求引用文件与行号证据；无证据的问题降级为建议级 |
| 三选一协议退役后 v1.0 演示叙事断裂 | 面试叙事升级为「从可控到既自主又可信」：默认 Build 是信任用户，底线守卫+checkpoint 是信任的底气（§14） |

## 14. 面试辩护要点（v1.1 增补 Q&A）

| 问题 | 回答要点 |
|---|---|
| 为什么默认 Build 而不是像 v1.0 默认 Plan？ | 高自动化是长任务的前提；安全不再依赖「先问后做」的流程摩擦，而是四层兜底（底线守卫/沙箱/checkpoint/审计）——信任用户但不失控 |
| 高风险确认为什么交给模型判断而不是硬编码规则？ | 风险是语义概念（改 1 行配置 vs 重构整个模块），规则表写不全；误判成本低（多确认一次），漏判有审批与 checkpoint 兜底 |
| checkpoint 为什么基于 Git 而不是自研快照？ | 工作区本就有 Git；stash create + 自定义 refs 得到「不动工作树、不污染 stash、不被 gc」的快照语义，零新依赖；自研快照要重做增量/压缩/一致性，是重复造轮子 |
| 会话切换为什么不动文件？ | 文件修改可能是跨会话共享的合法成果；Git 已是文件快照系统；文件回退必须是显式操作（/rollback）而非隐式副作用——职责分离 |
| 为什么评审用子 agent？主 agent 不能自己评吗？ | 自评审有确认偏置（评自己刚写的东西）；且评审需要完整 Spec 上下文，在主上下文里做会污染执行上下文——隔离同时解决质量与预算 |
| Spec 为什么是一等公民而不是 Plan 的加强档？ | 大小任务是两类工作形态：小任务要快（直接干），大任务要严谨（规格+评审+逐任务验收）；两轨道各自纯粹，比「一个流程带开关」概念更清晰 |
| Spec 进入前为什么强制先澄清？ | 评审循环的成本高（3 轮 × 全文评审），需求不清就起草等于让用户为返工买单；澄清前置把返工消灭在最便宜的阶段 |
| 评审为什么有轮次上限？ | 终止条件是 agent 的第一责任（v1.0 五类终止条件的延伸）；不设上限的评审循环就是新的死循环 |
| 子 agent 为什么禁止嵌套？ | 第一版以确定性优先：串行队列行为可预测、审计归属清晰；嵌套的调度与预算治理留给后续版本 |
| 新增的这堆命令会不会让界面复杂？ | 命令增长但视觉原则不变：常规操作单行摘要，只有人介入时刻才升格卡片；/sessions、/specs 列表卡是「按需查看」不是常驻噪音 |

## 15. 与 v1.0 设计的对照速查

| 主题 | v1.0（概设 v4.1） | v1.1（本文） |
|---|---|---|
| 默认模式 | Plan（只读） | Build（auto-approve + 底线守卫） |
| Plan→Build 切换 | submit_plan 三选一 | 退役；/plan、/build 显式切换 + 高风险主动确认 |
| 会话存储 | <workspace>/.glaucous/sessions/ | ~/.glaucous/sessions/<project-hash>/ + 索引 |
| 方案锚 | plans/ 轻量锚 + read_plan | 保留；Spec 轻量锚 + read_spec 同款机制 |
| 审计 | mode_switch/model_switch/审批 | + checkpoint、子 agent 归属字段 |
| 非目标 | 多 agent 协作不做 | 串行子 agent 做；并行/嵌套仍不做 |
| 终止条件 | 五类 | 五类不变；评审循环轮次上限为其延伸 |
