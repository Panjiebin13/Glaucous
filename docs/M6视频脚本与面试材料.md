## 第一部分：2 分钟演示视频脚本（演示任务：让 Glaucous 写一个简易版 coding agent）

**叙事策略**：演示任务选「有真实工程量的 meta 任务」——**让 Glaucous 从零实现一个简易版编程智能体**（对话循环 + 工具调用 + 测试）。它一箭三雕：①工程量真实可见（多文件、主循环、工具系统、测试）；②完整走一遍 /spec 全流程（澄清→评审→逐任务执行→代码评审→验收）；③结尾「agent 写出的 agent 真的能跑」是全片最强镜头。长等待一律 4~8 倍速 + 字幕标注。

**素材准备**（录制前必须完成）：
- 干净演示工作区：`/tmp/agent-demo`（`git init` + 初始提交）；产物 mini-agent 建在这里，不要建在 Glaucous 仓库内；
- **务必先完整预演一遍该任务**：验证能成功走完 /spec 全流程、记录真实耗时（决定加速倍数）；预演成功的那次会话可直接作为录制素材；
- 建议的任务表述（口径见下）：`/spec 从零实现一个简易编程智能体（Python）：与 OpenAI 兼容模型对话的主循环、工具调用（read_file 与 shell 两个工具）、流式输出解析与步数上限终止，附 pytest 测试`；
- **澄清阶段作答口径**（控制规模防跑飞）：目标边界选「单包三文件以内、不含权限系统与上下文压缩」；验收口径选「测试全绿 + 能实际完成一次读文件任务」；
- 终端字号放大；确认画面不出现 API key（不执行 env 打印类命令）；录屏 1080p 即可。

## 第二部分：1 分钟项目介绍（英文口述稿 + 中文翻译）

### English Script（正式使用，约 165 词，正常语速 55~65 秒）

> Hello, professors. My project is **Glaucous**, a coding agent built entirely from scratch — no agent framework. Its goal is **high autonomy on long tasks, with minimal interruption to the user**. Three design lines support this.
>
> **First, to run long tasks well.** A large task goes through the Spec flow: the agent first clarifies requirements through an interactive interview, then writes a written specification with a task list and acceptance criteria. An isolated reviewer sub-agent audits it, and the main agent executes the tasks one by one, followed by a code-review loop and an acceptance check. Because sub-agents run in isolated contexts, and I built a four-level context compression pipeline, the context stays small even after dozens of steps.
>
> **Second, clear requirements before acting.** The Spec flow starts with mandatory clarification, and users can fork a session to discuss ideas first — so interruptions only happen when they truly matter.
>
> **Third, safety as the foundation of autonomy.** Every task turn takes a Git snapshot, so any damage can be rolled back with one command. My permission matrix opens up whatever checkpoints can cover, and strictly blocks what they cannot.
>
> All core logic — the main loop, streaming parsing, context management, tool execution, error handling — is self-implemented, with 336 passing tests. Thank you.

**语速提示**：三条主线段各约 15 秒；「Second」最短（10 秒）留出缓冲；若超时，优先砍第三段第二句（权限矩阵句）与结尾自研列表（保留 336 tests）。

### 中文翻译（对照版）

> 各位老师好，我的项目是 **Glaucous**——一个完全从零实现的编程智能体，没有使用任何 agent 框架。它的目标是：**高自主地跑长任务，尽可能少打扰用户**。三条设计主线支撑这一点。
>
> **第一，让长任务跑得动。** 大任务走 Spec 流程：agent 先通过交互式访谈澄清需求，然后写出一份含任务清单和验收标准的书面规格；由隔离的评审子 agent 审查，主 agent 逐任务执行，之后还有代码评审循环和验收核验。因为子 agent 在独立上下文中运行，加上我实现的四级上下文压缩管线，长任务跑几十步上下文占用仍然很低。
>
> **第二，先明确需求再动手。** Spec 流程以强制澄清开场，用户还可以 fork 会话先讨论想法——所以只有真正重要的时刻才会打扰用户。
>
> **第三，安全是自主的前提。** 每轮任务自动打 Git 快照，任何破坏都能一条命令回退；权限矩阵放开 checkpoint 能兜住的一切，坚决拦住兜不住的。
>
> 核心引擎——主循环、流式解析、上下文管理、工具执行、错误处理——全部自研，336 个测试全部通过。谢谢。

（中英两版同构，均约 1 分钟；正式面试用英文版，中文版供准备与对照）

## 第三部分：两者如何互补 + 面试预判问答

**互补关系**：视频回答「它真的能干活吗」（证据：真实任务全流程 + 回退高光），1 分钟介绍回答「你为什么这么设计」（逻辑：宗旨 → 三主线）；两者共用「三条主线」同一叙事骨架，评委看完视频听介绍时锚点完全对应。面试深入追问则以《实现详解》§七决策速查应对。

**高频追问预案**：

| 可能的问题 | 回答要点 |
|---|---|
| 为什么选「写一个简易版 coding agent」作为演示任务？ | 它有真实工程量（主循环/工具系统/测试多文件），能完整走通 Spec 全流程；且产物本身能跑，现场运行一次即可证明 agent 真的具备编码能力——比修 bug 类小任务更能展示长任务自主性 |
| 为什么不用 LangChain 等框架？ | 赛事要求自研是一方面；更本质是框架的抽象与我要的「细粒度权限/上下文工程」冲突——比如工具派发要接审批管线、压缩要按轮次结构裁剪，自研才能逐层控制 |
| 上下文压缩为什么分四级？ | 成本递增、侵入性递增：L0 截断零成本保信息（落盘可回取）；L1 本地派生摘要零模型开销；L2 模型压缩有开销但保语义；预算耗尽优雅终止是最后防线。水位 70%/85% 分级触发，避免过早压缩损失近期上下文 |
| 子 agent 为什么只做串行？ | v1 的评审场景串行足够（父等报告）；并行需要调度/合并/权限并发控制，复杂度与当前收益不匹配，已在计划表登记为 v2 增强 |
| checkpoint 为什么不用 stash？ | `git stash create` 捕获不了 untracked 新增文件，「新增文件被移除」的回退验收点会落空；改用临时索引 write-tree 方案，不碰工作树和真实索引 |
| 权限为什么这么设计？ | 核心判据是「有无兜底」而非「操作吓人程度」：有快照兜底的区内写放开（否则长任务每步弹卡，高自主不成立）；区外/运行时目录/远端无兜底必须拦。`.glaucous/` 恒拦是因为快照刻意排除它且审计防篡改是底线 |
| 模型输出解析失败怎么办？ | 连续 3 次解析失败熔断终止本轮；终止前为悬空 tool_call 补推失败结果——不补的话历史序列非法，整个会话会被 API 400 永久报废 |
| 怎么保证实现不偏离 Spec？ | 四道：任务消息内联「不越界」约束、Spec 锚随时可回读、事后代码评审对照 diff 查越界、验收逐条核验 |
