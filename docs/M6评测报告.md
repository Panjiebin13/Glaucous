## 一、方法论：为什么不用权威公开数据集

业界三个权威基准与本项目的不适配分析：

| 基准 | 形态 | 不直接采用的原因 |
|---|---|---|
| **SWE-bench / Verified** | 真实仓库 issue→PR，测试判定，2294/500 实例 | ① 每实例需 docker 镜像与完整大仓库环境，搭建工程量大；② 单实例需在数十万行代码库导航，**单次运行 token 消耗以百万计**；③ 需集成官方 `swebench` harness；④ 以上均超出截止时间（9/2）与资源约束。**另有本质原因**：SWE-bench 只测「修单个 issue」这一环节，无法度量 Glaucous 的核心主张——Spec 全流程、上下文工程、安全兜底机制 |
| **Aider polyglot** | 225 道多语言练习 | 任务为单函数级编辑，粒度小，无法体现「长任务」叙事 |
| **Terminal-Bench** | 终端任务基准 | 需容器环境，同样受时间与工程约束 |

**本报告采用的方法**：自建任务集，但**判定方法与 SWE-bench 同构**——
1. 每个任务配**客观测试判据**（`check.sh`：pytest 全绿 / 文件断言 / 行为断言），自动判定，零主观分；
2. 按 **pass@1** 口径：每任务单次运行，不重试刷分；
3. 判据先经「人工标准答案」自验（三个 check.sh 均验证输出 PASS，对应 SWE-bench 的 gold patch 验证）；
4. **全程留痕可复现**：每次运行实例保留于 `/tmp/eval-<case>-<时间戳>`（产物 + .glaucous 会话与审计），可复查。

## 三、实测结果（v1.1 组，2026-08-31 23:22~23:50）

| 用例 | 结果 | 人工干预次数 | 上下文峰值占用 | token 消耗 | 用时 | 备注 |
|---|---|---|---|---|---|---|
| e1 | **PASS** | **0** | 2%（2.4k/128k） | ↑27.6k ↓1.2k（缓存命中 89%） | ~2 分钟 | 一轮完成；自主选 unittest（零依赖）编写 3 用例；遇 `python` 不存在自纠为 `python3` 并沉淀记忆 |
| e2 | **PASS** | **0** | 8%（10.2k/128k） | ↑51.4k+↑39.9k，↓3.2k（缓存命中 94~95%） | ~15 分钟 | 全自主完成四目标：9 个 pytest 用例、pyproject 依赖分组（test/dev）、README；自主处理 `pip install -e ".[test]"` 依赖安装 |
| e5 | 任务段成功（回退段待演示） | 0 | 2%（2.8k/128k） | ↑31.5k ↓1.8k（缓存命中 89%） | ~6 分钟 | 重构完成且 8 测试全绿；判定 FAIL 为**预期状态**（文件已改、未回退），实例保留供 /rollback 演示 |

**关键观察**：
1. **零干预达成**：三个用例在默认 Build + auto-approve 下全程无人工干预完成——「减少干扰」宗旨的直接证据（区内写免审 + 危险命令定级放行的权限矩阵生效）；
2. **上下文极低占用**：最复杂的 e2（多文件工程化 + 依赖安装 + 测试）峰值仅 8%——四级上下文工程（L0 截断/L1 裁剪/方案锚）在长任务下的实测效果；
3. **自纠能力**：`python` 不存在 → 自动切 `python3` 并沉淀记忆（跨用例复用）；
4. **自主但知边界**：e5 中模型主动说明「重构后增加了类型校验…若你希望放宽或收紧，告诉我即可调整」——自主决策伴随显式边界声明。

## 六、诚实声明与局限

1. 单模型（deepseek-v4-flash）、每用例单次运行——结果为方向性证据，非统计显著结论；
2. 自建任务集（非公开基准），规模小（3 用例实测 + 6 用例定义待补）；判据客观但任务覆盖面有限；
3. 管道模式隐藏了交互细节（澄清访谈、审批卡未参与本次自动运行）——这部分由视频演示补足；
4. e2 中模型有轻微范围外扩（自主补充 .gitignore/CI/lint 配置），未判为越界（属工程化目标的合理延展且未破坏判据）——如实记录。
